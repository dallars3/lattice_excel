# 行级范围「仅自己」越权返回 3001：接受记录存在性的信息披露

「可填写」协作者越权修改、删除、撤销删除、回滚或读取他人记录历史时，记录域统一返回 3001（角色无此操作权限）；记录不存在或已软删除仍返回 4002。该决定接受「可填写用户可感知某条记录是否存在」的信息披露，以换取与 AC-PERM-03 及前端错误映射一致的语义。

## 背景

PRD 的角色矩阵规定「可填写」只能编辑、删除、撤销、查看自己创建的记录；AC-PERM-03 要求越权请求由服务端拒绝并提示无权限（3001）。修复前记录域在行级范围「仅自己」下把他人记录与不存在/已删除记录一律映射为 4002（记录/字段已被删除），导致：用户看到「对象已被删除」的误导提示；前端按 4002 走「刷新」恢复策略，而不是 3001 的全局只读降级；验收用例无法区分「没有权限」与「记录真的没了」。

## 考虑过的替代方案

- **继续统一返回 4002（完全不披露存在性）**：信息面最小，但违反 AC-PERM-03 的「拒绝并提示无权限」口径，前端无法触发只读降级，且与网关 CheckAccess 的 3001 语义割裂。
- **统一返回 3001（连不存在也报无权限）**：能统一文案，但把「记录已被删除」误报为权限问题，破坏 4002 的刷新/冲突恢复路径，也与接口文档的错误码约定冲突。
- **返回 3002 或 1001 等其他码**：3002 专指外部协作者禁导出，1001 表示参数非法，均不表达行级越权。

## 决策

- 记录存在且创建者不是当前用户：更新单元格、批量更新、删除记录、撤销删除、回滚、读历史统一返回 3001。
- 记录不存在或已软删除（不可操作）：仍返回 4002，不与权限拒绝混淆。
- 判定顺序固定为「先存在/可操作性，后归属」：撤销删除先确认记录处于可撤销的软删除态，回滚先确认历史节点与记录可达，再判断创建者，保证两类错误码稳定可区分。
- 批量更新的逐 op 结果在 `error_code` 中返回 3001，不中断同批其他 op。

## 后果

- 「可填写」用户可借助记录的 3001/4002 差异探测某个 record_id 是否存在。披露范围限于其本就有权访问的 Base，且 3001 只暴露「存在但无权」，不返回记录内容；换取的是错误码语义与 AC-PERM-03、前端全局只读降级完全一致。
- 查询视图与单条读取仍以 4002 隐藏他人记录，信息披露仅出现在写路径与历史读取这两个需要明确拒绝原因的场景。
- 记录域后续新增越权用例必须显式断言 3001，不存在/已删除用例断言 4002，避免两类语义再次漂移。
