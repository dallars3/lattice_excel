# backend-align：对齐结论后端待改动全集（#1~#3 基础能力 + N1~N8 契约补全）

Status: resolved

## Problem Statement

协作多维表格仓库此前为纯后端三服务 + HTTP/WS 契约，前端工程已在仓库根 `web/` 立项（M1），但网关没有任何前端产物托管能力，单机试运行无法同源交付页面；需求文档附录 C 约 30 条对客埋点事件没有上报去处（审计通路是服务间事件消费，不对客户端暴露）；PRD FR-08-1「在线即时可见」与现有契约之间缺少通知推送通道。同时《接口文档-v0.6》与需求/前端技术方案经 2026-11-05 全量核对，还存在 8 项契约缺口（N1~N8）：分组出参平铺、行级评论角标无字段、字段描述缺失、字段宽度无持久化、公式错误原因对客不可得、分享链接入口未实现、WS 路径文档与实现矛盾、复制记录无专用接口。前端按现有契约无法实现需求 4.5 组头、4.7 行内角标、PRD FR-03-2 字段说明、FR-03-4 错误原因与分享入口跳转。《前后端对齐结论-v0.1》于此列出全部后端待改动，且每项均已对照仓库代码逐条核实。本 spec 将基础能力三件套与契约补全八项合成为一份可执行的后端改动规格。

## Solution

基础能力三件套（对齐结论 #1~#3）：

1. 网关具备同源托管前端构建产物的能力：构建期嵌入产物、非 API 路径回退入口文档（history 路由）、API 与 WS 路由保持优先。
2. 新增轻量对客埋点端点：登录后鉴权、批量上报、事件时间与用户由服务端兜底、按事件幂等；数据链路与操作审计彻底分流，经事件总线异步落库，不新增 gRPC 契约。
3. 通知实时推送（P1）：WS 契约新增通知帧，网关按用户寻址推送「失效提示」，前端收到后仍以拉取接口取数，30 秒轮询保留为兜底。

契约补全八项（对齐结论 N1~N8，全部按推荐方案裁定）：

- N1 分组在 P0 降级为「分组字段作第一排序键」的排序展示语义，组头不显示全量计数；分组段结构与全量计数 P1 另立。
- N2 记录页出参增行级未解决评论计数（批量聚合 map），不动单记录主体结构。
- N3 字段增描述：P0 建字段即写入、查询即返回；编辑通道 P1。
- N4 字段宽度按视图存（视图配置增宽度 map），复用既有视图配置全量替换通道。
- N5 公式错误值以哨兵前缀编码贯穿契约与落库，重算状态帧增原因透传。
- N6 网关新增分享链接重定向入口，复用既有链接解析与注册携带通道。
- N7 WS 路径文档升版对齐实现。
- N8 复制记录 P0 以读+建组合实现（后端零改动），原子接口 P1 可选。

## User Stories

1. As a 前端开发者, I want 网关同源托管前端构建产物, so that 单机试运行无需单独静态服务器或 CDN。
2. As a 前端开发者, I want history 路由深链（如 /bases/abc）刷新时返回入口文档, so that 任意页面直刷与收藏链接都不 404。
3. As a 前端开发者, I want 带内容 hash 的资产获得长缓存而入口文档每次校验, so that 发版后用户拿到新入口而不必重拉未变资产。
4. As a 前端开发者, I want API 与 WS 路径优先于静态回退, so that 现有 93 条 HTTP 契约与实时通道行为不变。
5. As a 后端开发者, I want 前端尚未构建时后端仍可编译, so that 纯后端开发不依赖 node 工具链。
6. As a 部署者, I want 一条脚本串起「前端构建 → 产物嵌入 → 后端编译」, so that 不出现前端已出包、后端未嵌入的交付事故。
7. As a 后端开发者, I want 静态托管以文件系统接口注入实现, so that 可用内存文件系统做单测而无需真实产物。
8. As a 产品运营, I want 前端 30 余条埋点事件有服务端上报去处, so that 能按动作级事件做使用分析。
9. As a 前端开发者, I want 埋点端点登录后鉴权, so that 匿名流量无法伪造用户行为。
10. As a 数据使用者, I want 事件里的用户与接收时间由服务端兜底, so that 客户端时钟错误或被篡改不影响数据可信度。
11. As a 前端开发者, I want 埋点支持整批上报（上限内多条一次提交）, so that 不产生每事件一次的连接开销。
12. As a 前端开发者, I want 事件按客户端 id 幂等去重, so that 重传不造成重复计数。
13. As a 前端开发者, I want 单条非法事件只计拒绝而不回绝整批, so that 个别脏数据不拖累整批埋点。
14. As a 后端开发者, I want 埋点走事件总线异步落库, so that 埋点洪峰不反向压垮网关与核心写入链路。
15. As a 后端开发者, I want 埋点存储与操作审计彻底分流, so that 审计不可删语义不被埋点量级污染。
16. As a 运维, I want 埋点数据有保留期自动清理, so that 存储成本有界。
17. As a 前端开发者, I want 上报失败时前端静默丢弃且不重试放大, so that 埋点绝不阻塞产品功能。
18. As a 用户, I want 新通知到达时在线页面即时感知, so that 不必等 30 秒轮询窗口。
19. As a 前端开发者, I want 通知推送帧只做失效提示不带全量数据, so that 帧小巧且客户端仍以拉取接口为唯一数据源。
20. As a 前端开发者, I want 同一用户的所有在线连接都收到通知帧, so that 多标签页场景不遗漏。
21. As a 前端开发者, I want 通知帧不参与快照与重放序号, so that 断线重连语义不被破坏（重连后由拉取接口兜底）。
22. As a 前端开发者, I want 30 秒轮询保留为兜底, so that 推送上线期间行为可回退、离线错过可补齐。
23. As a 前端开发者, I want 分组视图在 P0 以「分组字段作第一排序键」落地, so that 组头渲染在窗口按需加载模型下可确定性实现。
24. As a 产品, I want P0 分组仅排序的边界与不显示全量计数的口径写明在契约中, so that 联调期不产生组头计数的预期歧义。
25. As a 前端开发者, I want 记录页每行获得未解决评论计数（随页批量返回）, so that 行内评论角标与未读数可渲染。
26. As a 前端开发者, I want 行级计数以一次聚合返回而非逐行请求, so that 大页渲染不产生 N+1 开销。
27. As a 用户, I want 悬停字段名查看说明文本, so that 字段语义对协作成员自解释。
28. As a 字段创建者, I want 创建字段时写入说明文本, so that P0 即具备说明的录入与展示通路。
29. As a 用户, I want 字段宽度拖拽调整后在其他会话仍生效, so that 表观布局不因刷新丢失。
30. As a 前端开发者, I want 宽度配置挂入视图配置并按视图生效, so that 各视图独立布局且复用既有配置更新通道。
31. As a 用户, I want 公式出错时能看到具体原因, so that 除数为空等错误可自助定位。
32. As a 前端开发者, I want 公式错误值有确定的前缀编码, so that 网格、详情与历史视图的值解析逻辑一致。
33. As a 前端开发者, I want 重算完成帧携带错误原因, so that 实时态无需额外查询即可呈现原因。
34. As a 外部访客, I want 打开分享链接被带到对应 Base, so that 分享链路从入口到落地可用。
35. As a 未登录访客, I want 分享链接跳转登录/注册并保留链接上下文, so that 登录或注册后直达分享目标。
36. As a 前端开发者, I want WS 连接路径与接口文档一致, so that 联调不因文档脱节踩坑。
37. As a 前端开发者, I want 复制记录在 P0 以读+建组合语义实现, so that 需求 4.4 不阻塞且无需后端新接口。

## Implementation Decisions

- 静态托管形态：构建期嵌入前端产物（go:embed），非 API 路径回退入口文档；复用标准库多路器「最具体模式优先」保证 API 与 WS 路由不被吞。
- 嵌入兜底：嵌入目录内置占位文件，前端未构建时仍可编译；产物目录不入库；部署入口收敛为单一构建脚本（前端构建 → 拷贝 → 后端编译）。
- 缓存策略：带内容 hash 的资产 immutable 长缓存；入口文档短缓存校验；不走 API 管线的禁缓存头。
- 埋点通道形态：网关校验、盖章后经事件总线发布 `track.reported`（可靠投递：消费组 + ack），core 服务新增消费者批量落库，与既有 import/audit 消费者同套路。
- 埋点端点契约：`POST /api/v1/tracking/batch`，登录后鉴权；请求 `{events:[{event_id,event_name,detail,client_at_ms}]}`，响应 `{accepted,duplicated,rejected}`；单批上限、event_id 长度、event_name 格式（`fe_` 前缀）、detail 大小均有校验；服务端兜底 `user_id`/`user_type`/`received_at_ms`。
- 幂等双保险：网关侧短期去重（Redis SETNX，故障放行）即时报 duplicated；落库表对 event_id 唯一约束再兜底。
- 限流：埋点端点纳入既有限速管线独立桶（按来源 IP），防埋点放大；埋点端点自身不产生埋点。
- 存储：新增埋点表与操作审计分离，迁移成对、表名全局唯一（护栏自动校验）；附保留期清理任务。
- 通知推送：WS 帧契约新增 `Notification` 消息（编号顺延），含通知 id、类型、所属 Base、发生时间；复用 worker 已发布的 `notify.created` 事件，订阅即推送，通知生产侧零改动。
- 按用户寻址：hub 在既有房间广播之上增加按用户 id 的连接索引；通知帧无序号、不进快照与重放，客户端收帧后按原拉取接口刷新。
- 分组 P0：记录查询把视图分组字段前置为第一排序键；出参结构不变；契约写明「分组仅排序、组头无全量计数」。分组段结构、组间排序与全量组计数 P1 另立。
- 行级角标：记录页响应顶层增「记录 id → 未解决评论数」映射；每页一次批量聚合（已打开状态评论、命中页内记录集）；单记录主体结构不动。
- 字段描述：字段对象增 description（长度上限）；建字段入参支持；P0 只做建+读，编辑通道 P1。
- 字段宽度：视图配置增「字段 id → 宽度（px）」映射，视图级存储；更新通道复用既有视图配置全量替换接口。
- 公式错误：错误值编码定为字符串哨兵前缀 `#ERROR:` 后跟原因（无原因时仅 `#ERROR`），落库、记录读取、历史读取统一该编码；重算状态（实时帧与服务间响应）增原因字段；求值服务已产出原因，不改生产逻辑。
- 分享入口：网关新增 `GET /s/{link_token}` 路由：调既有链接解析 rpc 取 Base；短期缓存链接上下文（TTL<60s）；302 重定向——已登录至 Base 页、未登录至登录/注册页并携带 token；复用既有注册携带 token 的通道。
- WS 路径：接口文档总览表对客实时行升版为按 Base/Table 的真实实现路径（对齐实现，不改代码）。
- 复制记录：P0 前端组合实现（读+建），后端零改动；P1 原子接口可选。
- 文档联动：接口文档 v0.6 → v0.7 一次收口（新增埋点/入口/通知帧条目与静态托管说明、N1/N2/N3/N4/N5/N7 对应章节、三处裁定说明）；前后端对齐结论 v0.1 → v0.2 更新全部状态。
- 护栏口径（全批）：P0 全部改动落在消息级与网关路由级，不新增 rpc（计数 111 不变）；P1 备选项（分组聚合接口、描述编辑、原子复制）若新增 rpc，须同步护栏期望值；proto 改动后跑重生成脚本；新增迁移 up/down 成对。

## Testing Decisions

- 好测试标准：只测外部行为，不测实现细节——静态托管测「给定文件系统与请求路径，输出状态码、缓存头、回退内容」；埋点路由测「给定请求，输出的校验结果、盖章字段与发布的事件」；推送测「给定事件，目标用户收帧且他人不收」；分组测「给定视图配置与记录集，输出按组键排序的行序」；角标测「给定页内记录与评论分布，计数映射与未解决数一致」；描述/宽度测「创建/查询/更新的往返内容」；公式错误测「给定求值错误，落库与帧的编码及原因一致」；入口测「给定 token 与登录态，重定向目标与上下文缓存写入」。
- 接缝（已确认，全部沿用既有，不新增）：静态托管经文件系统接口注入 + 内存文件系统；埋点网关层沿用表驱动路由测试，发布侧经事件总线内存实现断言，core 消费者仿既有审计/导入消费者的内存总线测试挂载；通知推送仿既有 hub 广播测试，以内存总线发事件断言收帧；core 侧契约改动仿既有工作区/审计消费者与内部服务的测试挂载；契约帧以 proto 编解码测试兜底。
- 覆盖底线：静态托管（深链回退、API/WS 防御、缓存头、空产物编译）；埋点（鉴权、批量上限、逐条校验、幂等、服务端兜底字段、限流）；通知推送（按用户寻址、多连接均收、他人不收、无序号不参与重放）；契约八项每项一个正常路径与一个边界（空分组、无评论、超长描述、未知 token、无原因错误）；文档升版项以文档护栏脚本全绿为准。

## Out of Scope

- 前端 tracker 采集器与 30 余条埋点的前端调用点（前端 M1 已声明不实现）。
- 埋点数据分析侧（报表、聚合、导出）。
- 通知推送的可靠投递升级与红点缓存推送等增强；对齐结论 #5 的「导入中」徽标可选项。
- CDN / 对象存储等替代静态托管形态。
- N1 P1：分组段结构、组间排序与全量组计数；N3 P1：描述编辑通道；N8 P1：原子复制接口。
- 字段宽度的字段级全局方案（已裁定视图级，不再另做）。
- 错误值的弹窗与文案设计（前端侧）。
- 分享链接的安全加固（令牌轮换、防爆破等）超出本批最小实现。

## Further Notes

- 裁定冻结（按推荐方案）：N1 排序降级、N4 视图级、N8 组合实现；其余项无争议直接实施。
- 波次：基础能力优先——静态托管随前端 M1 收口联调；埋点端点与契约修订批各自独立实施；通知推送 P1 与埋点同属事件链、可并行；文档升版统一在收口里程碑一次完成。
- 护栏自检：新增迁移 up/down 成对；本 spec 带 Status 行；通知帧与消息级改动涉及 proto 重生成脚本；完成后跑文档护栏脚本。
- 命名沿用仓库既有风格：事件命名（`notify.created`、`track.reported`）、测试挂载、消费者注册均对齐既有先例。
