# 排序/筛选竞态修复 · N7/N5/N2 收尾 · p1p2 E2E 存量失败清零

Status: ready-for-agent

## Problem Statement

web-m2-fixes 与 acceptance-defect-remediation 两批交付后的验收压测与全量回归暴露三类问题：

1. **排序/筛选竞态（P1 产品缺陷，压测实锤）**：视图配置面板（排序/筛选/分组）的任何改动——单字段连续正降切换、跨字段切换、双字段组合排序、筛选连续换字段、筛选+排序组合——**首次改动几乎必然不生效**，网格停留在旧顺序/旧筛选结果，后续改动表现为「结果永远慢一拍」。数字、文本、单字段、多字段全部命中。用户需要反复无意义操作或刷新页面才能看到预期结果。14 行数据压测（web/e2e/sf-stress.spec.ts 六条 TC）两次全量复跑稳定失败，证据链完整：后端 H-48 排序/筛选本身正确（curl ASC/DESC 双向验证）、H-47 配置保存成功（服务端配置含 sort_list）、失败在前端「配置保存与记录重取的竞态」——本地配置即时更新使记录查询签名变化，React Query 立即用新 key 重取记录，而此刻携带新配置的保存请求尚未落库，后端按旧配置返回数据，旧结果被缓存到新 key 下且不再重取。
2. **N7/N5/N2 收尾遗留**：注册自动建企（N7）落地后产生了既定的语义后果——邀请成员加入企业的流程对几乎所有用户失效（新注册用户必然已自有企业，而接受邀请的前置条件是「用户无企业归属」），企业级成员扩展事实上不可用；核心测试基建另有迁移锁间歇失败问题（golang-migrate 驱动硬编码 10 秒锁等待，高负载下全量迁移重放偶发超窗）。
3. **p1p2 E2E 存量失败（14 条，首次真跑暴露）**：p1p2.spec.ts 的夹具此前一直被注册语义阻断、从未真正运行；夹具适配后全量首跑 37 过 / 14 败 / 3 跳。14 条失败均为存量用例体缺陷或行为漂移的累积暴露——其中排序/筛选族（TC-060-02 筛选操作符抽样、TC-060-04 排序、TC-060-08 筛选无结果）与竞态缺陷同源；其余（类型转换预览的类型串写法、alert 选择器误命中常显横幅、TSV 复制空内容、粘贴提示、排序计数、筛选空态、附件缩略图、外部导出可见性、键盘全程编辑器可见性、埋点批次为 0、分享链接入口、超链接）需逐条 triage：区分「改用例」「修产品」「确认行为后关闭」。

## Solution

- **竞态修复**：视图配置保存成功回调（onSaved）按保存后的数据条件签名使记录列表查询失效并重取，保证网格展示的数据永远对应当前已保存的配置；保存在途期间的中间状态不得把旧配置结果缓存到新签名 key 下。修复后压测用例（SF-01..06）全部转绿，作为回归证明随本批提交。
- **邀请流语义修复**：接受邀请不再要求「用户无企业归属」——邀请任何活跃用户；接受即为目标企业新增一条成员行（保留用户既有企业归属与自有 Base 访问，不迁移不清空用户的企业字段）；企业内权限按成员行判定。实现时必须验证跨企业场景的鉴权链（用户访问其作为成员（非当前企业）的企业下 Base 是否可用），若现有鉴权仅按用户的企业字段判定则一并修正为按成员行判定。
- **迁移锁重试**：测试基建的迁移执行（含全量重放路径）增加锁等待重试包装（短退避多次），消除高负载下的偶发「无法获取锁」失败。
- **p1p2 14 条失败清零**：逐条 triage 并处置——排序/筛选族经竞态修复后回归验证；其余逐条判定为「修用例」（选择器/类型串/期望值漂移）或「修产品」（确认为真实回归），最终 p1p2 全量套件通过（或对确属废弃的用例以显式跳过+理由收口）。

## User Stories

1. As a 表格使用者, I want 在排序面板选择排序字段与方向后表格立即按新顺序展示, so that 我不需要反复操作或刷新页面。
2. As a 表格使用者, I want 连续多次切换正序降序时每次切换都立即生效, so that 对比数据只需要点两下。
3. As a 表格使用者, I want 从按数字排序切换到按文本排序时立即按文本顺序展示, so that 不同维度对比顺畅无卡顿。
4. As a 表格使用者, I want 设置两级排序（如数字升序+文本降序）后表格按组合顺序展示, so that 多维度整理数据符合预期。
5. As a 表格使用者, I want 并列值的次级排序稳定生效, so that 同值记录按我的次级规则排列。
6. As a 表格使用者, I want 排序中空值行按「统一排最后」的口径展示, so that 空数据不干扰有效数据的阅读。
7. As a 表格使用者, I want 添加或修改筛选条件后表格立即只显示满足条件的记录, so that 筛选结果即改即得。
8. As a 表格使用者, I want 连续更换筛选字段与操作符时每次都立即生效, so that 逐个维度排查数据不需要刷新页面。
9. As a 表格使用者, I want 筛选生效时再切换排序方向, 二者叠加即时呈现, so that 组合分析不被打断。
10. As a 表格使用者, I want 清除全部筛选后立即恢复全量记录, so that 退出筛选状态零等待。
11. As a 企业所有者, I want 按用户名邀请任何活跃用户加入我的企业（无论对方是否已有自己的企业）, so that 企业级协作不再受注册顺序限制。
12. As a 被邀请的用户, I want 接受邀请后成为目标企业成员且我已有的企业与其下 Base 不受影响, so that 加入协作不牺牲我自己的数据。
13. As a 企业所有者, I want 被邀请加入的成员按其角色访问企业内 Base, so that 企业协作权限与单企业场景一致。
14. As a 回归开发者, I want p1p2 全量 E2E 套件 54 条用例全部通过或有理有据的显式跳过, so that 该套件重新成为可信回归资产。
15. As a 回归开发者, I want 排序/筛选族失败在竞态修复后按原断言复跑通过, so that 确认产品行为回归正常而非放松断言。
16. As a 回归开发者, I want 每条存量失败用例有明确的 triage 结论（修用例/修产品/关闭+理由）, so that 后续维护者理解每条处置。
17. As a CI 执行者, I want 迁移重放在高负载下不再偶发锁超时失败, so that 测试基建稳定可信。
18. As a 表格使用者, I want 上述排序/筛选行为在数字、文本等各字段类型下表现一致, so that 心智模型统一。
19. As a 表格使用者, I want 14 行以上数据量下上述行为全部成立, so that 真实数据规模下无隐藏缺陷。
20. As a 验收者, I want 本批压测用例（SF-01..06）随修复提交并全部转绿, so that 竞态修复有可重复的回归证明。

## Implementation Decisions

- **竞态修复（核心）**：视图配置自动保存的成功回调（onSaved）在保存完成后按保存结果的数据条件签名失效记录列表查询并等待重取完成；修复必须覆盖排序、筛选、分组三条路径（同一签名机制）；保存请求与记录重取的顺序语义为「先落库后取数」——禁止把保存完成前的旧配置响应缓存到新签名 key 下（React Query 缓存语义按此校准，必要时取消在途请求）。
- **修复的验证口径**：压测用例 sf-stress.spec.ts（已存在于 web/e2e/，随本批提交）六条 TC 全部转绿——覆盖 14 行数据、数字/文本、连续 4 次正降切换、跨字段切换、双字段组合（值对序列断言）、筛选两轮 12 次切换、筛选+排序组合。
- **邀请流语义**：移除「目标用户须无企业归属」前置（邀请与接受两处）；接受邀请 = 目标企业新增成员行（角色按邀请时的授予），**不修改用户的企业字段、不迁移既有 Base**；企业内鉴权按成员行判定——实现票必须先验证现有鉴权链在「用户是成员行归属（非当前企业字段）」场景下对目标企业 Base 的访问是否成立，不成立则修正鉴权为按成员行；为此新增 Go 集成用例（邀请自有企业用户→接受→访问目标企业 Base 全链路）。
- **迁移锁重试**：测试基建中执行迁移（Up/Down/重放）的入口统一包一层锁等待重试（指数退避，如 2s/4s/8s 三次），仅作用于测试库；不改 golang-migrate 驱动本身。
- **p1p2 triage 流程**：逐条记录 triage 结论到该用例的注释（修用例/修产品/关闭+理由）；「修产品」项必须先在该表构造失败复现再修复；排序/筛选族三条在竞态修复合并后优先复跑。已知分类供参考：类型串写法与 alert 选择器误命中常显横幅属修用例；外部导出对外部协作者的可见性、键盘全程编辑器可见性、埋点批次为 0 需核实是否真实回归（后者疑似 tracking 消费链路问题）。
- **兼容红线**：不改 H-46/H-47/H-48 接口契约；不改变「空值统一排最后」的排序语义；不改注册/邀请限速；不放宽 p1p2 既有断言（只允许修正用例体自身的缺陷）。

## Testing Decisions

- **好测试标准**：只测外部行为——「改排序方向后整列值序列立即变化」「加筛选后行数立即变化」「邀请自有企业用户并接受后能访问目标企业 Base」；断言按值序列而非记录 ID（并列组内顺序不确定）。
- **接缝（全部沿用现有）**：
  1. 压测用例 sf-stress.spec.ts 对部署栈直接运行（竞态修复的回归证明，先提交该文件再修）。
  2. Go 集成测试（独立测试库，票 01 护栏自动生效）：邀请流全链路、迁移重试行为。
  3. 前端组件级/MSW：人员目录等既有用例保持绿。
  4. p1p2.spec.ts 全量（--workers=1）作为最终收口门。
- **prior art**：web-m2-fixes 的 m2-fixes.spec.ts（账号前缀/限速规避/幂等守卫）、ad-fixes.spec.ts（三缺陷验收口径）、sf-stress.spec.ts（值序列断言）。

## Out of Scope

- 实时协作推送（WS 接线属 M3）；视图配置保存的服务端响应结构扩展。
- 用户多企业切换 UI（一期接受邀请后以成员行授予访问，不提供企业切换器）。
- p1p2 之外其他 E2E 套件的存量问题；测试对共享 Redis 的 FlushDB 行为（另行评估）。
- mainline（feature/p0-mvp）与本批分支的合并（属分支管理，由用户拍板时机）。
- 上批已记录的编辑器下拉去重等技术债。

## Further Notes

- 竞态缺陷的完整证据链：压测 spec 两次全量稳定复现（首次改动不生效）→ curl 直接验证后端 ASC/DESC 双向排序正确 → 诊断脚本慢速操作「碰巧」正常（PUT 先于 GET 落库时正常，竞态输掉时异常）→ 前端机制链（面板 onChange → 自动保存钩子即时 PUT → 本地配置即时更新 → 数据条件签名变化 → React Query 新 key 立即重取）中「重取先于落库」即命中旧配置。
- 压测数据与断言口径：14 行（负数/零/重复/空数字/空文本/中英文混排），空值统一排最后（后端既定语义，面板提示与实现一致）；文本排序为 utf8mb4_0900_ai_ci 码点序。
- p1p2 14 条失败的完整清单与逐条失败断言已留存：F:\codex\wt\web-m2-int\out\p1p2-run.log（TC-000-06 分享链接入口、TC-040-10 超链接、TC-040-13 公式 #ERROR、TC-040-16 类型转换预览、TC-050-06 TSV 复制、TC-050-07 粘贴只读列跳过、TC-050-11 排序视图禁拖、TC-060-02 筛选操作符抽样、TC-060-04 排序、TC-060-08 筛选无结果、TC-070-06 缩略图、TC-080-05 外部导出恒隐、TC-170-03 键盘全程、TC-180-03 关键事件触发；3 条跳过为同族变体）。
- 修复顺序建议：竞态修复 → p1p2 triage（排序/筛选族先复跑）→ 邀请流语义 → 迁移锁重试 → E2E 全量收口。
- 部署口径：修复合并后重建部署（web_api + core 均有改动），压测与回归对部署栈验证。
