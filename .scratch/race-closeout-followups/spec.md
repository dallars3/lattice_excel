# 竞态收口遗留项整改：测试 Redis 隔离、视图查询稳定性与 E2E 可信度

Status: ready-for-agent

## Problem Statement

`race-closeout-remediation` 的票 05 在最终 E2E 收口后记录了四个需要独立跟进的问题：

1. **核心测试破坏共享 Redis 消费链路**：Go 集成测试直接对共享 Redis 执行 `FlushDB`，会删除 live stack 正在使用的 Streams 消费组。消费循环没有在运行期恢复缺失消费组的机制，因此 calc、notify、tracking、audit 等服务可能在测试结束后持续停摆，直到人工重建消费组或重启服务。
2. **网格偶发长时间停滞**：7 轮全量回归中有 3 次出现写入后记录查询最长约 120 秒仍不渲染新数据的情况，涉及排序或分组视图以及普通写入场景。单跑和重跑通常恢复，当前尚无足够 trace 证明唯一根因。视图配置保存、记录查询 key 切换、查询取消、写入后的行刷新之间可能存在交错。
3. **P0 新增记录用例存在基线计数竞态**：用例在网格与列头出现后立即读取记录数量，而首窗口记录可能仍在加载。实测基线曾从临时的 1 条变化为实际的 5 条，导致“新增三入口”断言在错误基线上执行并偶发失败。
4. **三个弹层编辑器 E2E 被错误跳过**：多选、人员、关联字段的验收 helper 在搜索词仍非空时只按一次 Enter。当前编辑器契约规定：搜索词非空时 Enter 只执行匹配或勾选，搜索词清空后的下一次 Enter 才提交已选集合。因此 E2E 没有走完真实提交链，却把结果记录成“编辑器提交后不收起”的产品缺陷，并长期以 fixme 跳过。

这些问题同时影响环境安全、产品可信度与回归资产可信度。维护者和 CI 不应因为运行测试而破坏 live stack；表格使用者不应在写入或切换视图后长时间看不到结果；回归执行者应能依赖确定性的 E2E 基线，而不是把正确的编辑器行为错误标记为产品缺陷。

## Solution

以四个独立但按顺序收口的工作流解决遗留问题：

- **测试 Redis 隔离与消费组自愈**：所有测试使用专用 Redis 隔离入口，禁止对 live stack 所连接的 Redis 逻辑库执行清理；同时让可靠消费订阅在消费组缺失时限频重建消费组并继续消费，作为 Redis 被清理、重启或数据丢失后的防线。
- **网格记录查询去竞态**：建立可重复的延迟/乱序反馈环，将视图配置面板的乐观草稿与真正驱动记录查询的服务端确认配置分离；只有视图配置保存成功后才启用新的数据条件签名。记录查询使用精确取消与超时，不接受旧配置响应污染新 key，也不依赖整表取消和全局失效。
- **P0 网格就绪语义确定化**：网格明确暴露首窗口记录是否就绪；E2E 在初始记录加载完成后以 H-48 服务端基线校验 UI，再执行新增操作。每次新增同时验证服务端数量与 UI 最终数量。
- **编辑器验收语义修正**：保持现有多选编辑器“搜索非空时 Enter 只勾选、搜索清空后 Enter 提交”的产品契约。修正 E2E helper 在点击候选后清空搜索再提交，解封 TC-040-07/09/14，并补齐单选项点击提交与多选二次 Enter 提交的回归覆盖。

建议落地顺序为：Redis 测试隔离与消费组自愈 → P0 网格就绪语义 → 编辑器 E2E 语义修正 → 网格停滞专项 trace 与查询状态收口。前三项应形成确定性闭环；网格停滞必须先由失败 trace 证明实际卡点，再完成对应修复。

## User Stories

1. As a 开发维护者, I want 在 live stack 运行时执行完整 Go 测试而不清空共享 Redis, so that 测试不会让线上验证实例的业务消费者停摆。
2. As a 表格使用者, I want 后台测试与验收任务运行期间继续正常收到计算、通知、埋点和审计事件, so that 测试活动不会造成业务功能静默失效。
3. As a CI 执行者, I want 所有测试 Redis 客户端通过统一的隔离入口创建, so that 新增测试不会再次意外使用 live stack 的逻辑库。
4. As a 测试基础设施维护者, I want 清理 Redis 前执行逻辑库与目标地址的硬校验, so that 不安全的清理在连接建立阶段就失败并给出明确原因。
5. As a 本地开发者, I want 默认测试 Redis 使用专用逻辑库或专用实例, so that 无需每次人工选择隔离环境。
6. As a 部署环境, I want 测试逻辑库不可用时通过显式配置切换到独立 Redis 实例, so that 受限 Redis 部署仍能运行测试且不会回退到共享库。
7. As a 可靠事件消费者, I want 读取时发现消费组缺失可以限频重建消费组, so that Redis 被清理或重启后不需要人工执行 `XGROUP CREATE`。

## Implementation Decisions

### 范围与顺序

- 本规格只覆盖票 05 Comments 中前四个可执行遗留项；第五条“疑似并行重复 E2E 执行痕迹”仅作为备查事实，不进入本批实现。
- 四个工作项应在实现票中拆分并保持可独立验收。建议顺序为 Redis 隔离与自愈、P0 网格就绪、编辑器 E2E 修正、网格停滞 trace 与查询状态收口。
- 不以放宽产品断言来关闭问题。允许修正测试 helper、测试就绪语义和错误归类，但不得弱化排序、筛选、分组、写入落库或编辑器提交的既有验收断言。

### 测试 Redis 隔离

- 新增统一的测试 Redis 入口，测试配置使用独立逻辑库或独立 Redis 实例，生产与 live stack 继续使用原配置，不新增业务 API 契约。
- 默认测试隔离目标必须与 live stack 目标不同。入口在创建客户端和任何清理动作前执行硬校验；发现目标仍指向共享逻辑库时直接失败并说明所需配置。
- 测试清理只能通过该隔离入口执行。核心与 worker 测试中的直接 `FlushDB` 调用全部移除或改为隔离入口；测试辅助客户端读取 session、登录锁、Streams 等 key 时必须连接同一隔离目标。
- 若部署 Redis 禁用逻辑库，允许通过显式测试地址切换到专用实例；不得在未显式确认隔离的情况下回退到共享 Redis。
- Redis 隔离以保障环境安全为第一目标，不以“运行结束后再重建共享消费组”作为替代方案。

### Redis 消费组自愈

- 可靠订阅在读取 pending、claim 或读取新条目时识别“消费组不存在”错误，并通过 EventBus 的 Redis bridge 重建消费组。
- 重建动作应限频并带可观测日志；成功后立即继续原消费循环，不得要求进程重启。
- 群体重建沿用现有可靠投递语义：从 Streams 可用起点创建消费组，结合 event_id 幂等与 outbox 状态机防止重复业务副作用。
- 恢复路径不得把临时 Redis 错误当作毒消息 ack 丢弃，也不得退出消费 goroutine。
- 该能力是共享 Redis 被外部清理、Redis 重启或消费组元数据丢失后的运行期防线，与测试隔离同时存在。

### 网格记录查询

- 先建立确定性反馈环：在组件级/MSW 测试中控制视图配置保存和记录查询的延迟、失败与完成顺序，稳定复现“旧配置响应晚到”“保存与查询交错”“连续配置切换”三类时序。
- Playwright 对网格停滞场景启用失败保 trace，并覆盖连续排序、筛选、分组切换与写入的串行压力场景。trace 至少能区分 H-47 未完成、H-48 未启动、H-48 已启动未返回、响应已返回但 UI 未提交。
- 将配置状态拆分为面板乐观草稿与已确认数据配置。面板继续即时反馈用户操作；筛选、排序、分组的数据条件签名只取最后一次 H-47 成功返回的配置。
- 视图配置保存继续合并连续改动并串行提交。保存成功后提交该次的已确认配置；若仍有更新草稿，等待其保存，避免中间配置驱动无意义的记录查询。
- 记录查询在 key 切换时允许旧 key 请求结束，但其结果只能留在旧 key；不得再次依赖“取消整张表所有记录查询后全局失效”作为正确性保证。
- 记录查询接入 React Query 提供的取消信号，HTTP 层将取消传递给实际请求。每次记录查询增加统一超时，默认 15 秒；超时产生可重试错误态，不无限保持 loading。
- 新配置查询进行中可保留上一个已确认结果作为临时展示，但必须显示“正在应用视图条件”或等价状态，避免用户把旧数据误认为新条件结果。查询成功后替换为当前已确认配置的数据。
- 继续使用服务端游标窗口与虚拟滚动，不引入全量轮询、无限重试或一次性全量拉取。
- 现有数据条件签名只包含完整筛选、排序和分组；字段显隐、列宽、冻结列、行高等纯展示配置不触发表级记录重拉。

### P0 网格就绪

- 网格暴露明确的首窗口记录就绪状态，可同时提供 `aria-busy` 与测试可读状态；状态只在首窗口数据已提交到 UI 后变为就绪，不以网格容器或列头出现作为记录就绪。
- P0 的通用 `gotoBase` 等价行为等待网格、列头与首窗口记录三重就绪。
- TC-050-01 在操作前通过 H-48 获取服务端首窗口基线，并等待 UI 数量与基线完全一致后再保存 `before`。
- 三个新增入口每次执行后都验证服务端记录数量达到预期增量，并等待 UI 最终数量与同一预期一致。
- 不使用固定 sleep 解决加载竞态。新增或复用现有轮询等待 helper，错误信息应指出“记录首窗口未就绪”或“服务端/UI 数量未一致”。

### 下拉编辑器验收

- 不改变现有产品契约：单选点击候选即提交并收起；多选点击候选只切换勾选；搜索词非空时 Enter 只匹配或勾选；搜索词清空后 Enter 提交完整集合。
- 修正多选、人员、关联 E2E helper：完成全部候选点击后显式清空搜索框，再按 Enter 提交，并等待编辑器隐藏与目标单元格展示期望标签。
- TC-040-07、TC-040-09、TC-040-14 从 fixme 解封。原 fixme 理由更新为“验收 helper 未完成搜索清空后的提交动作”，不再记录为产品缺陷。
- 组件测试补充或明确四条契约：多选点击保持打开、搜索非空 Enter 不提交、搜索清空 Enter 提交并收起、单选点击立即提交并收起。
- 本批不引入新的编辑器交互按钮或改变键盘状态机；如后续增加“完成”按钮，应另立 UX 票，不阻塞上述验收。

### 兼容性与契约

- 不修改 H-46、H-47、H-48 的请求或响应契约，不新增服务端字段，不改变游标分页与空值排序语义。
- 不改变权限、写链乐观锁、幂等键、离线只读或实时协作语义。
- 不改变多选、人员、关联编辑器的产品键位语义。实现票必须复用现有组件测试与 E2E 断言，而不是通过重写需求来适配测试。

## Testing Decisions

### 好测试的标准

- 只测试用户可观察行为和系统外部契约：live stack 消费者继续工作、Redis 消费组可在缺失后恢复、网格显示与已保存视图配置一致、P0 记录数量同时与服务端和 UI 一致、多选编辑器在真实完整操作后提交并收起。
- 不直接断言私有函数次数、内部日志文本或某个 helper 是否被调用；日志只用于失败诊断。
- 对时序问题使用可控延迟、乱序完成和确定性轮询，不使用随机压力或固定 sleep 作为唯一复现手段。
- 对共享状态问题同时验证“操作前后外部状态不变”，例如 live Redis 的消费组在测试执行前后存在且 pending 状态未被测试清理。
- 对“旧响应晚到”测试，断言最终缓存中只有当前已确认配置的数据，不要求旧请求物理上永远不存在。

### 测试接缝

1. **测试 Redis 隔离入口**：沿用现有 testmysql 护栏思路，在其上新增 Redis 专用入口的单元/集成验证。该接缝验证安全目标拒绝、专用目标清理、所有测试辅助客户端一致连接。
2. **Redis EventBus 订阅行为**：使用现有 fake Redis bridge 的订阅测试接缝注入消费组缺失错误，断言重建成功后下一条事件被正常交付。再以真实隔离 Redis 和 live stack smoke 验证 Streams 消费组不被 Go 全量测试清理。
3. **视图保存到记录查询链路**：优先在现有 Base 工作台组件与 QueryClient/MSW 接缝控制 H-47/H-48 完成顺序，覆盖连续配置切换、旧响应晚到、查询超时与重试。现有 sf-stress 继续作为真实部署栈的值序列验收。
4. **P0 网格就绪与新增记录**：沿用现有 Playwright P0 接缝和 API request context。先增加受控 H-48 延迟场景证明旧 helper 会误取临时数量，再验证就绪 helper 与服务端基线断言转绿。
5. **下拉编辑器**：组件层沿用现有编辑器注册表测试；部署栈层沿用 p1p2 的 TC-040-07/09/14 与真实键鼠输入，不在测试中直接调用组件提交回调。

### 必测模块与验收

- **Redis 测试基建**：不安全目标拒绝、安全目标正常连接与清理、session/锁/Streams 辅助 client 共用同一目标。
- **可靠事件订阅**：消费组缺失后重建、恢复后继续消费、重建失败限频重试、现有 ack/幂等行为不回退。
- **Base 工作台与记录查询**：数据条件签名只在服务端确认配置后切换；旧 key 响应不进入新 key；连续保存最终查询正确；15 秒超时进入可重试错误；游标窗口与字段显隐等展示配置行为不变。
- **P0 网格**：首窗口加载前不报告就绪；加载完成后 UI 与服务端基线一致；三个新增入口分别按服务端/UI 双断言通过。
- **下拉编辑器**：多选点击保持打开、搜索非空 Enter 只勾选、搜索清空 Enter 提交收起、单选点击立即提交；TC-040-07/09/14 解封并转绿。

### Prior Art

- MySQL 测试隔离护栏已经采用“统一测试连接入口 + 非测试目标硬失败 + 前后快照证明共享库未变化”的模式；Redis 隔离应沿用同一安全思想。
- 可靠事件订阅已有重复 event_id 只处理一次、空闲后继续轮询、外部事件无 outbox 行仍消费的测试，可扩展消费组缺失恢复分支。
- 视图数据加载已有游标、虚拟滚动、空值与分组排序测试；本批只在配置保存与查询 key 生命周期上收口，不重建加载模型。
- P0 与 p1p2 已采用 Playwright 真实浏览器、真实键鼠输入、API 校验和 `expect.poll`/`toHaveCount` 等确定性等待模式。
- 编辑器已有点击、方向键、搜索词非空 Enter、第二次 Enter 提交、单选点击提交等 41 条组件测试；E2E 应复用这些已确认的业务语义。

### 最终回归门

- Go 全量测试在 live stack 运行下执行，live Redis 的现有 Streams 消费组在测试前后保持可消费；模拟删除消费组后，服务在限频窗口内自愈。
- 视图竞态专项组件测试、sf-stress、p0、p1p2 串行运行通过；网格停滞专项在失败时产出 trace，修复后连续重复执行不出现 120 秒级停滞。
- P0 TC-050-01 连续重复执行 20 次零失败，且受控慢 H-48 场景不会在初始数据加载完成前开始计数。
- TC-040-07/09/14 正常执行，不再以 fixme 跳过；相关编辑器组件测试继续全绿。

## Out of Scope

- 修改 H-46/H-47/H-48 或其他 HTTP/gRPC 契约；扩展 ViewConfig 服务端版本号。
- 重做记录加载模型、放弃游标分页、引入全量轮询或前端持有全量 Table 数据。
- 改变多选、人员、关联编辑器的既有键盘交互，或在本批新增“完成”按钮与新的弹层信息架构。
- 处理票 05 第五条“疑似并行重复 E2E 执行痕迹”；该条保持备查记录。
- 修复本批四个问题之外的其他 E2E flake、产品 UX 缺陷或 Redis 高可用架构。
- 为 live stack 增加自动执行测试清理、自动重启或人工运维替代方案。
- 在 Redis 数据完全丢失后从数据库 outbox 重新发布全部历史事件；本批只保证消费组缺失后的运行期恢复与幂等。
- 修改权限、注册、邀请、写链乐观锁、幂等键、离线只读或实时协作语义。

## Further Notes

- 第 1 项是真实环境安全问题：消费组只在订阅建立时创建，运行期缺失不会自动恢复；不能仅以“测试结束后人工 `XGROUP CREATE`”作为长期方案。
- 第 2 项当前仍缺少唯一根因证据。规格要求先建立失败 trace 和受控乱序测试；查询状态分层、精确取消与超时是解决已识别竞态的系统方案，最终提交应记录 trace 指向的实际失败分支。
- 第 3 项的根因属于 E2E 就绪语义，不是产品记录查询错误。修复应以显式就绪信号和服务端基线替代临时 DOM 数量。
- 第 4 项经组件实现与现有 41 条编辑器测试确认，当前产品契约正确；TC-040-07/09/14 的问题是 helper 只执行了“选择/勾选”而没执行“清空搜索后的提交”。
- 本规格使用项目领域词汇：Table、Record、View、ViewConfig、协作者、单元格；不用“工作表”“行数据源”“筛选器缓存”等非规范替代词。
- 实现时继续遵守 ADR 中的视图游标加载模型与自研网格渲染约束；任何与既有键盘状态机或 EventBus 可替换接口冲突的改动，应先记录决策再实施。
